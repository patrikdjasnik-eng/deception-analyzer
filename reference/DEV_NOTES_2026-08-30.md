## LLM a backend

Pracovali jsme také na lokální LLM vrstvě.

Aktuální směr:

- Qwen 2.5 Coder 7B jako základní model
- později silnější 14B model
- 14B už byl předtím lokálně spuštěn a ověřen
- komunikace je navržená přes OpenAI-compatible llama-server API
- backend používá FastAPI
- LLM service řeší health check, běžný chat a streaming

Byla zpřesněna error handling logika LLM služby, aby HTTP chyby z lokálního LLM serveru měly jednotné chování.

Přidali jsme také `LlmPolicy`, která odděluje bezpečnostní pravidla konverzace od samotné komunikace s modelem.

Policy aktuálně řeší:

- prázdnou konverzaci
- maximální počet zpráv
- maximální délku zprávy

K policy byly přidány testy.

## CI a červené křížky u commitů

Narazili jsme na červené křížky u starších commitů:

- `8ab1a0e904cffe7b87c196de3a0e38fb9208cb56`
- `703af4ad6f8f8b4c93b428e0ae77c9362e313b04`
- `cf71447630a38bc2e0aff29fe4c31e060ca637f2`

Kontrola přes GitHub API neprokázala, že by na těchto SHA skutečně existoval neúspěšný workflow run. U kontrolovaných commitů nebyly dostupné relevantní status checks/workflow výsledky.

Z toho důvodu jsme se rozhodli staré commity nerevertovat ani uměle neopravovat. Historie zůstává zachovaná.

Poučení pro další vývoj: stav CI budeme ověřovat přímo podle konkrétního SHA a nebudeme označovat run jako důkaz úspěchu nebo selhání konkrétního commitu, pokud to GitHub API jednoznačně nepotvrdí.

## Co jsme si stanovili jako cíl MVP

MVP má být aplikace, kterou uživatel skutečně spustí na svém PC, nikoliv pouze backendová ukázka.

Požadovaný výsledek:

- UI co nejpřesněji 1:1 podle referenčního HTML
- všechny hlavní dashboardy
- navigace
- skutečné funkce místo statických placeholderů
- FastAPI backend
- lokální LLM
- Qwen 2.5 Coder 7B
- možnost následně použít 14B
- streaming chatu
- testy
- health checks
- lokální spuštění na PC

Autonomní cybersecurity agent se sandboxem není podmínkou první verze MVP. Je plánovaný jako další fáze.

## Budoucí agent

Po stabilizaci MVP chceme postupně přidat agenta, který bude mít kontrolovaný přístup k obranným cybersecurity nástrojům běžícím v kontejnerech.

Plánovaná bezpečnostní vrstva:

- sandbox
- Docker kontejnery
- allowlist nástrojů
- řízený terminal
- timeouty
- resource limity
- audit log
- omezená oprávnění
- vyhodnocování bezpečnostní situace
- řízené reakce na rizika
- pravidelné reporty
- notifikace uživatelům

Agent nesmí dostat nekontrolovaný přístup k host systému jen proto, že umí pracovat s terminalem. Přístup musí vést přes bezpečnostní orchestration vrstvu.

## Co jsme dnes vyřešili

1. Nemohli jsme spolehlivě dostat původní HTML přes chat.

Řešení: HTML bylo vloženo přímo do repa jako `reference/rabbithollow-v3_4.html`.

2. Hrozilo, že při převodu do Reactu začneme UI domýšlet.

Řešení: reference v repu je zdroj pravdy pro 1:1 UI.

3. Starší commity ukazovaly červené křížky.

Řešení: ověřili jsme SHA přes GitHub API. Nebyl potvrzen skutečný failed workflow run, takže jsme historii neměnili.

4. LLM error handling potřeboval sjednotit.

Řešení: HTTP chyby jsou zpracované konzistentně na úrovni LLM service.

5. Bezpečnostní pravidla pro chat byla příliš těsně spojená s transportem.

Řešení: vytvořili jsme samostatnou `LlmPolicy` vrstvu a její testy.

6. UI bylo zatím příliš blízko jednoduchému chat MVP.

Řešení: začal se stavět skutečný RabbitHollow shell a jednotlivé pracovní dashboardy.
